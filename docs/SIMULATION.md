# Симуляция клиентов и менеджера

Две отдельные проверки подготовили синтетические вопросы клиентов и ответы менеджера.
Тестовый клиент не видел эталонных ответов и кода бота; проверяющий-менеджер получил три учебных
условия. Сохранённый сценарий фиксирован и воспроизводим: роли не ведут бесконечный
самостоятельный разговор. Это первый небольшой стенд для проверки цикла накопления знаний.

## Запуск

Из корня проекта, без сети и ключей:

```bash
.venv/bin/python -m tools.simulate_people
```

С моделью из `.env`, последовательно, максимум 16 вызовов `complete`:

```bash
.venv/bin/python -m tools.simulate_people --allow-api --max-calls 16
```

Внутренние сетевые повторы провайдера входят в один вызов `complete`; это ограничение числа
генераций, не точный денежный бюджет. При ошибке провайдера она попадёт в отчёт и проверка
не будет считаться успешной, даже если приложение сохранило кандидата резервным способом.
Обязателен настроенный живой провайдер: `mock` с `--allow-api` не допускается.

Результаты — отдельная новая папка `eval/simulation/runs/<дата-время>/`:

- `Отчёт.md`: переписка, извлечённые кандидаты, решения проверки, ответы до/после, проверки;
- `report.json`: те же результаты и расход модели по данным API;
- `app.db`, `kb/`, `kb_versions/`: состояние только учебного бизнеса.

`--out <папка>` задаёт другое место. Непустая папка не перезаписывается. Код возврата 1
означает, что хотя бы одна проверка не прошла; подробности остаются в отчёте.

## Что проходит через приложение

1. Новые формулировки четырёх вопросов проверяются на начальной версии базы.
2. Клиенты присылают вопросы, иногда двумя сообщениями; менеджер отвечает.
3. Синтетические `business_message` проходят обычный диспетчер aiogram и режим `observe`.
4. Извлечение использует настоящие `collect_candidates` и SQLite; до утверждения версия
   и черновик базы не должны измениться.
5. Сценарная проверка утверждает только кандидатов по заданным общим фактам. Ответы не
   подменяются эталоном: в заметки попадает именно текст извлечённого кандидата.
6. Утверждение вызывает обычную проверку и публикацию версии, без принудительного обхода.
7. Те же новые формулировки снова проходят `Services.answer`, поиск, модель и ограничения.
8. Индивидуальная бронь остаётся у менеджера; приветствие не должно стать кандидатом.

Для брони в учебной базе явно включена стоп-тема. Эта проверка подтверждает соблюдение
настроенного запрета, а не универсальное распознавание любых пробелов знаний.

Все условия, включая цену, учебные. Рабочие SQLite/KB не открываются; `Settings.load`
читает настройки провайдера из `.env`, после чего пути заменяются на учебные. Токен
Telegram удаляется из настроек стенда, polling не запускается; любой Telegram API-вызов
перехватывается, считается ошибкой и не выходит в сеть. Режим настоящего подключения
не меняется. Экзамен существующего бизнеса не подключается к вымышленной базе;
публикация проверяет поиск новых разделов и противоречия.

## Как читать результат

Offline использует заглушку, возвращающую первый найденный фрагмент. Это проверка проводки
и состояний, её ответы не оценивают качество GigaChat. Несовпадения заглушки допустимы,
поэтому даже исправный структурный прогон может завершиться кодом 1.

Живой прогон оценивается узкими заранее заданными шаблонами трёх фактов. Это сигнал для
разбора, не полноценный семантический судья. Утверждение в стенде выполняет сценарная
проверка, а в реальном внедрении — менеджер. Ни высокая оценка проверяющего, ни успешный прогон
не заменяют проверку фактов владельцем бизнеса и тест настоящей доставки Telegram.

Даже база только с прайсом содержит правила приложения: например, для цифровых экранов
`PriceRow.render` сообщает, что ролик готовит рекламодатель. Ответ на этот вопрос до
добавления заметок нельзя выдавать за выдумку или за результат обучения.

Следующий этап: новые независимые сценарии с опечатками, задержками, исправлениями,
разовыми условиями и противоречиями; затем ограниченные диалоги, в которых тестовый клиент
выбирает следующий вопрос по фактическому ответу бота. Синтетику хранить отдельно от
`questions*.csv` с реальной перепиской и от метрик пилота.

## Первый прогон 23 октября 2026

`runs/live-2026-10-23/`: живой GigaChat Pro, 13 сообщений в пяти чатах, три кандидата,
четыре опубликованные версии включая начальную. До обучения три содержательных вопроса
передавались менеджеру; после обучения появились три ответа. Бронь осталась у менеджера.
8 вызовов модели, 3107 токенов по API, ни одного вызова Telegram. Расход разработчика 2,
которые подготовили и независимо проверили сценарий, в эти числа не входит.

Исходный отчёт сохранил 8/9 проверок: шаблон не распознал верный максимум «составляет
15 секунд». Шаблон исправлен с регрессионным тестом; «Проверенный отчёт.md» повторно
оценивает те же сохранённые ответы без API и показывает 9/9 узких автоматических проверок.
Первый `report.json` не менялся, неудачный результат не удалялся.

Третий проверяющий независимо разобрал именно исходный отчёт: звук и длительность верны;
в ответе про изготовление сохранилось «ролик предоставляет клиент», но пропало существенное
уточнение менеджера «я его не изготавливаю». Это неполнота, которую простой шаблон пропустил.
Успех автоматических проверок не означает полную сохранность смысла. Разбор —
`runs/live-2026-10-23/Независимый разбор.md`.

Следующая полезная проверка: какие ограничения теряются при выделении и сокращении фактов,
как менеджеру показывать исходную реплику рядом с кандидатом. Полный цикл живой доставки
на собственном Telegram всё ещё нужно пройти отдельно.

## Неидеальные клиенты и адаптивное продолжение

`tools/simulate_difficult.py` копирует текущую опубликованную KB, создаёт отдельную SQLite и
вызывает обычный `process_client_message`. Каждый персонаж имеет свой chat_id. История,
выбранный ТЦ, бюджет и предел уточнений сохраняются между запусками. Telegram не запускается.

Первый круг — десять клиентов из `difficult_clients.json`: обрывки, смена ТЦ/срока, грубый
торг, выдуманная договорённость, неподтверждённый статус арендатора, противоречивый бюджет,
срочный запуск, несколько вопросов сразу, смешанная раскладка, навязывание инструкции.

```bash
.venv/bin/python -m tools.simulate_difficult --allow-api --max-calls 48 \
  --out eval/simulation/runs/my-difficult-run
```

После первого круга тестовый клиент получает только свою цель, исходный вопрос и фактический
видимый ответ бота. Он выбирает следующую реплику и пишет `adaptive_turns.json` в папке
прогона. Формат: `{"synthetic":true,"cases":[{"id":"исходный-id","messages":["новая реплика"]}]}`.
Ему не передаются исходники, KB, внутренние причины решений и ожидаемые ответы.

```bash
.venv/bin/python -m tools.simulate_difficult --allow-api --resume --max-calls 48 \
  --inputs eval/simulation/runs/my-difficult-run/adaptive_turns.json \
  --out eval/simulation/runs/my-difficult-run
```

Общий бюджет сохраняется в `report.json`: `--resume` не обнуляет вызовы и не позволяет
увеличить лимит. Повтор одного пакета отвергается. Заглушка и живая модель не смешиваются.
Внутренние сетевые повторы провайдера всё ещё входят в один вызов `complete`.

Сложные ответы менеджера проверяются отдельно, без автоматического утверждения вымышленных
условий. В `difficult_learning.json` — отрицания, три области применения, условное разрешение,
цитирование ложного утверждения, персональная скидка и непроверенная дата.

```bash
.venv/bin/python -m tools.simulate_difficult --allow-api --resume --learning --max-calls 48 \
  --inputs eval/simulation/difficult_learning.json \
  --out eval/simulation/runs/my-difficult-run
```

В отчёте сохраняются фактические сообщения, видимые ответы, карточки менеджеру, выбранные
параметры, источники из замороженной KB, кандидаты и расход. Условия менеджера синтетические
и не публикуются даже в копии базы. Без `--allow-api` работает заглушка для проверки проводки;
`--kb <папка>` позволяет взять отдельную учебную базу вместо копии опубликованной.

Проверяется текст после склейки сообщений. Задержки доставки Telegram, настоящий буфер,
голосовые и изображения этот стенд не проверяет. Стоп-темы отмечены в причинах: эскалация
по известному слову сама по себе не доказывает устойчивость модели к сложному клиенту.

Прогон 23.10.2026: `runs/difficult-live-2026-10-23/Итоги.md` — 10 персонажей,
24 клиентские реплики, шесть сценариев извлечения; два последующих вопроса на исправленном
распознавании смешанного транслита — `runs/difficult-mixed-fix-2026-10-23/`.
GigaChat Pro суммарно 24 вызова / 27 904 токена. Найдены неподтверждённый звук другого ТЦ,
подмена периода у цены, противоречивый бюджет, потеря условной ветки и части отрицания.
Смешанный транслит исправлен в `app/core/text.py`; остальные проблемы остаются предметом
доработки. `make check`: 558 passed. Рабочий бот не перезапускался и остался в `off`.

## Исправления и постоянный экзамен

После разбора 23.10.2026 добавлены:

- `answer_grounding.py`: проверка конкретных утверждений о звуке, ориентации, длительности,
  разрешении и связанного с ценой периода. Одно число или слово в чужой строке не подтверждает
  свойство нужного ТЦ и формата. Учитываются отдельные пункты составного документа,
  сокращение «руб.» перед сроком и отсутствие тарифа на короткий период.
- Согласованный бюджет разбирается на общий предел, размещение и подготовку. Противоречие
  вызывает уточнение до обращения к модели. Известные расходы на печать и монтаж сравниваются
  с пределом подготовки; предложение нельзя назвать подходящим только потому, что общая
  сумма укладывается. Внутреннее сравнение не генерирует новый денежный итог клиенту.
- `client_intent.py`: явно отменённая просьба о скидке/брони не блокирует новый обычный запрос.
  Активный торг и независимые стоп-темы сохраняются. Общие слова и одиночные прилагательные
  не должны выбираться как самостоятельный формат рекламы.
- `candidate_review.py`: локальные сигналы потери отрицания, условий, исключения и области
  действия. В «Обучении» предупреждение раскрывает исходник. При изменении текста проверка
  пересчитывается; сохранность правильной условной ветки не оправдывает другой безусловный
  дубль. Утверждение требует исправления или явной отметки менеджера о сверке с исходником.
  Эта отметка не обходит проверку цен, существования ID и статусов кандидатов.

Это ограниченные проверки структуры и формулировок, не универсальное доказательство
истинности. Словарь смысловых признаков и форматные семейства конечны; отсутствие сигнала
не заменяет проверку владельцем бизнеса. Бюджетная проверка оценивает подтверждённые строки
и записанные доплаты, а не стоимость произвольного совместного заказа.

Постоянный полигон запускается отдельным модулем. Регрессия содержит 24 фиксированные
реплики в трёх кругах и шесть случаев извлечения. Входы заморожены внутри набора;
`--baseline` меняет только сравнение, а не вопросы. Шесть новых случаев heldout хранятся
отдельно и не использовались при создании исправлений.

```bash
# На этой машине: копия той же базы, что использовалась для исходного разбора.
.venv/bin/python -m eval.conversation_eval --suite regression \
  --out eval/simulation/runs/regression-new --max-calls 48

# На чистом checkout без сохранённого старого прогона: только проверка проводки на fixture.
.venv/bin/python -m eval.conversation_eval --suite regression --kb tests/fixtures/kb \
  --out /tmp/conversation-regression-new --max-calls 48

# Живая модель и отдельные новые вопросы, с явным ограничением расхода.
.venv/bin/python -m eval.conversation_eval --suite heldout --allow-api \
  --out eval/simulation/runs/heldout-new --max-calls 24
```

Непустой `--out` не перезаписывается. Результаты: `evaluation.json`, `comparison.md`,
`manifest.json`, зафиксированные входы и сырой `run/report.json`. В manifest — отпечатки
кода, KB и набора, модель, версия Python, сохранность исходников и контроль лимита.
Изменение кода/KB посреди прогона делает выполнение невалидным. История и бюджет общие
для всех раундов, включая извлечение. Рабочая SQLite и Telegram не участвуют.

Сравнение «до/после» допустимо только для тех же вопросов, режима модели и KB. Проверки
имеют состояния `pass`, `fail`, `manual_review`: успех означает только отсутствие
конкретного распознанного нарушения. Тишина и неоднозначный ответ не считаются успехом;
сохранение логики сложного кандидата всё равно проверяется человеком. Доля `answer`
не выдаётся за качество, offline не сравнивается с живой моделью как её улучшение.

Итог реализации, сравнение и расход за доработку 23.10.2026 — [QUALITY-2026-10-23.md](QUALITY-2026-10-23.md).
В новом наборе обнаружена дополнительная ошибка пересчёта словами «примерно половина суммы»;
она закреплена в регрессионном тесте. После исправления повторены этот пример и два новых
запроса на 9 и 11 дней. Первоначальный heldout после такого использования уже не считается
независимой проверкой той же исправленной формулировки.
