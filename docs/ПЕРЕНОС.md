# Перенос на сервер

Схема: основной сервер в Москве (бот, админка, база, GigaChat, MAX) и маленький релей в Нидерландах только для Telegram:
с российских серверов api.telegram.org не отвечает. Переписка хранится только в России, релей ничего не хранит.
Разбор вариантов — `~/reports/Аренда сервера для бота.md`.

Переезд занимает около часа, бот молчит минут 10–20. Сообщения за это время не пропадут: Telegram хранит их до 24 часов
и отдаст, когда бот запустится (при запуске очередь не сбрасывается).

## Вариант без Telegram (решение 30.10: основной трафик в MAX)

Покупается только сервер в Москве, релей не нужен, шаги про него пропускаются. В `server.env` очистите
`TELEGRAM_BOT_TOKEN` и оставьте пустым `TELEGRAM_API_URL`, впишите `MAX_BOT_TOKEN`. Без токена Telegram бот не опрашивает его
и не шумит в логе повторами. Что это значит:

- наблюдение за Telegram на подключениях из базы прекращается, собранная переписка остаётся и переезжает;
- Telegram можно вернуть позже: купить релей, вписать оба значения и перезапустить, код менять не нужно;
- бот в MAX видит только сообщения в бот компании. Переписку менеджера с личного аккаунта MAX он не видит, такой
  возможности у MAX нет: клиентам нужно дать ссылку на бота;
- для первой проверки хватит долгого опроса: `MAX_WEBHOOK_URL` пустой, домен не нужен. Для рабочего режима MAX просит вебхук,
  см. раздел «Бот MAX».

## 1. Серверы

Основной: Ubuntu 24.04, от 1 vCPU и 2 ГБ. Снаружи открыт только порт 22, админка — через SSH-туннель.
До оплаты на тестовом сервере проверьте: `curl -m 10 https://api.telegram.org` (ожидаемо таймаут) и
`curl -m 10 -k https://ngw.devices.sberbank.ru:9443/api/v2/oauth` (ответ есть, код не важен).

Docker на основном сервере — по официальной инструкции docs.docker.com/engine/install/ubuntu (нужен Compose 2.30+).

Релей: самый маленький сервер в Нидерландах, домен (A-запись на его IP), порты 80 и 443 открыты:

```bash
sudo apt install -y caddy
sudo cp Caddyfile /etc/caddy/Caddyfile   # deploy/telegram-relay/Caddyfile
sudo nano /etc/caddy/Caddyfile   # замените {$RELAY_DOMAIN} и {$MAIN_SERVER_IP} прямо в файле
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl restart caddy
```

Журнал запросов на релее не включайте: токен бота идёт в адресе. Проверка с основного сервера:
`curl -m 10 https://tg.ваш-домен.ru/bot<токен>/getMe` — ответ `"ok":true`; с любого другого адреса — 403.

## 2. Репетиция (бот продолжает работать)

На компьютере, с основного сервера ничего не меняя:

```bash
.venv/bin/python -m tools.deploy bundle --out ~/assistant-rehearsal
```

Папка содержит `code.tar.gz` (код из последнего коммита), `data.tar.gz` (вся `data/`: база, переписка, версии базы знаний),
`server.env` (настройки без путей и ключа Яндекса) и `SHA256SUMS`. В папке переписка клиентов и ключи: права 700, не
выкладывайте её в облака и почту, переписка должна оставаться в России. Выполните шаг 4 и проверьте шаг 5, но **в
`server.env` очистите `TELEGRAM_BOT_TOKEN`**: второй бот с тем же токеном мешает живому и забирает его сообщения.

## 3. Переезд

Сначала закоммитьте всё, потом:

```bash
deploy/mac-autostart.sh off
.venv/bin/python -m tools.deploy bundle --final --out ~/assistant-move
scp -r ~/assistant-move root@<сервер>:/root/
```

`--final` откажется работать, если бот ещё запущен или есть незакоммиченные правки.
**С этого момента бот на Mac не запускайте**: два бота с одним токеном конфликтуют.

## 4. На сервере

```bash
cd /root/assistant-move && sha256sum -c SHA256SUMS
mkdir -p /opt/assistant && tar xzf code.tar.gz -C /opt/assistant
install -m 600 server.env /opt/assistant/.env
cd /opt/assistant
nano .env                 # TELEGRAM_API_URL=https://tg.ваш-домен.ru
./setup restore /root/assistant-move/data.tar.gz --yes
./setup check
docker compose up -d --build --wait
```

## 5. Проверка

- `docker compose logs app | tail` — «Run polling», без Traceback и TelegramConflictError.
- С ноутбука: `ssh -L 8000:localhost:8000 root@<сервер>`, затем http://localhost:8000 — вход тем же логином и паролем.
- «Наблюдение»: те же чаты и сообщения, что были. Подключения: те же режимы.
- Написать боту с другого аккаунта и увидеть сообщение в админке.

## Бот MAX

**Оформление (делает владелец профиля, в нашем случае дочь Кати, по своему номеру):**

1. Статус самозанятой должен быть уже оформлен: физлицо без статуса бота не создаст.
2. business.max.ru/self: вход по номеру телефона, тип профиля «Самозанятый», проверка через Госуслуги. Для самозанятых —
   до двух ботов.
3. Создать бота и отправить на модерацию (обычно несколько рабочих дней): название до 59 символов без эмодзи, описание до
   200 символов, логотип 500×500. Требования взяты из сторонних обзоров, в кабинете сверьте с актуальными.
4. Токен передать только через `.env` на сервере: кто знает токен, управляет ботом. В чат и почту его не слать.

Юридический владелец бота и профиля — та, на кого он оформлен. Кто отвечает за переписку клиентов как оператор
персональных данных и на каком основании бот работает на бизнес Кати, выясните у юриста и бухгалтера до запуска.

**Запуск на сервере:**

1. В `.env`: `MAX_BOT_TOKEN=…`, затем `./setup check` и `docker compose up -d`.
2. Катя пишет боту `/manager`. Любое новое подключение MAX, включая первое, ждёт «Разрешить» в админке.
3. Катя пишет `/mode draft`: первое время каждый ответ проверяет она. В базе новые подключения начинаются с наблюдения, в нём
   бот сам не отвечает.
4. Со второго аккаунта открыть ссылку из раздела админки «Клиенты в MAX» и написать боту как клиент. Эту проверку нельзя пройти
   одним аккаунтом: менеджеру бот как клиенту не отвечает.
5. Там же — QR-коды для печати, ссылки с меткой на каждое место и текст для старых клиентов. После запуска там видно, откуда
   пришли клиенты и кто оставил заявку. Формат ссылки — из документации MAX: `max.ru/<ник>?start=<метка>`.

Кнопка «Оставить заявку» запрашивает контакт клиента. Текст согласия и политику обработки данных нужно добавить до запуска с
настоящими клиентами: это отдельная задача, юрист должен проверить текст.

**Вебхук (рабочий режим).** Нужны домен с A-записью на основной сервер и открытые порты 80 и 443:

```bash
sudo apt install -y caddy
sudo cp deploy/max-webhook/Caddyfile /etc/caddy/Caddyfile
sudo nano /etc/caddy/Caddyfile   # замените {$MAX_DOMAIN} на bot.ваш-домен.ru прямо в блоке сайта
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl restart caddy
```

В `.env`: `MAX_WEBHOOK_URL=https://bot.ваш-домен.ru/max/webhook` (`MAX_WEBHOOK_SECRET` пакет переноса уже создал), затем
`docker compose up -d`. Бот подпишется сам и восстановит подписку, если она пропала. Пока сервер недоступен, MAX повторяет
доставку, но не дольше 8 часов: простой дольше потеряет сообщения. Наружу открыт только этот адрес, админка по-прежнему через
SSH-туннель. Убрали `MAX_WEBHOOK_URL` — бот снимет подписку и вернётся к опросу.

## 6. Если не получилось

На сервере `docker compose down` (без `-v`), на Mac `deploy/mac-autostart.sh` — бот вернётся к прежним данным. Сообщения,
полученные на сервере, в базе Mac не появятся.

## 7. После переезда

- Копии: `./setup backup /root/backups/assistant-$(date +%F).tar.gz` раз в сутки по cron и забирать к себе (`scp`).
  Ежедневные копии внутри тома пропадут вместе с сервером. Хранить только в России.
- После проверки удалить `/root/assistant-move` и `~/assistant-move`, в них переписка и ключи.
- `GIGACHAT_VERIFY_SSL=false` переехал как есть: ключ GigaChat идёт без проверки сертификата. На сервере лучше добавить в образ
  корневой сертификат Минцифры и поставить `true`.
- Нерешённое для настоящего пилота: GigaChat физлица — только для некоммерческого использования; уведомление
  Роскомнадзора об обработке персональных данных; ключ Яндекса на сервер не переносится, но отозвать его всё равно нужно.
- Копия нужна и файлу `.env`: без токенов и секрета бэкап данных не запустит бота.


## Проверки перед первым запуском новой версии (03.11.2026)

- В «Наблюдении» открыть «Какие чаты записывать» и разрешить только рабочие чаты. Новые чаты по умолчанию
  не записываются; в списке появится только их номер. Режимы подключений обновление не переключает.
- `/health` возвращает 503, если включённый MAX не готов или обработчик вебхука остановлен.
- Вебхук подтверждается после записи события в SQLite. При остановке очередь и склейка завершаются;
  если 40 секунд не хватило, события остаются для следующего запуска. Compose даёт остановке 60 секунд.
- Между отправкой в MAX и отметкой в SQLite возможен аварийный разрыв: повторная отправка тогда допустима.
  Полную гарантию «ровно один раз» без поддержки идемпотентности MAX не заявляем.
- Docker: часовой пояс Asia/Yekaterinburg, журналы максимум 3 файла по 10 МБ. Это не заменяет бэкапы.
- После удаления клиента из рабочей базы отдельно проверить старые бэкапы и утверждённые знания.
  При восстановлении старой копии удалённая переписка может вернуться.
- Черновик отдельного согласия: `docs/MAX-CONSENT.md`. До запуска с настоящими клиентами заполнить
  реквизиты оператора и согласовать текст; кнопки согласия ещё не реализованы.

Домены в `/etc/caddy/Caddyfile` задавайте непосредственно в блоке сайта: наличие `EnvironmentFile`
в системном юните Caddy не предполагается. Не заменяйте документированную проверку домена переменной из `.env` бота.
