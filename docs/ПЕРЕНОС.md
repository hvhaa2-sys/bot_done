# Перенос на сервер

Схема: основной сервер в Москве (бот, админка, база, GigaChat, MAX) и маленький релей в Нидерландах только для Telegram:
с российских серверов api.telegram.org не отвечает. Переписка хранится только в России, релей ничего не хранит.
Разбор вариантов — `~/reports/Аренда сервера для бота.md`.

Переезд занимает около часа, бот молчит минут 10–20. Сообщения за это время не пропадут: Telegram хранит их до 24 часов
и отдаст, когда бот запустится (при запуске очередь не сбрасывается).

## 1. Серверы

Основной: Ubuntu 24.04, от 1 vCPU и 2 ГБ. Снаружи открыт только порт 22, админка — через SSH-туннель.
До оплаты на тестовом сервере проверьте: `curl -m 10 https://api.telegram.org` (ожидаемо таймаут) и
`curl -m 10 -k https://ngw.devices.sberbank.ru:9443/api/v2/oauth` (ответ есть, код не важен).

Docker на основном сервере — по официальной инструкции docs.docker.com/engine/install/ubuntu (нужен Compose 2.30+).

Релей: самый маленький сервер в Нидерландах, домен (A-запись на его IP), порты 80 и 443 открыты:

```bash
sudo apt install -y caddy
sudo cp Caddyfile /etc/caddy/Caddyfile   # deploy/telegram-relay/Caddyfile
# в /etc/default/caddy: RELAY_DOMAIN=tg.ваш-домен.ru и MAIN_SERVER_IP=<IP основного сервера>
sudo systemctl restart caddy
```

Журнал запросов на релее не включайте: токен бота идёт в адресе. Проверка с основного сервера:
`curl -m 10 https://tg.ваш-домен.ru/bot<токен>/getMe` — ответ `"ok":true`; с любого другого адреса — 403.

## 2. Репетиция (бот продолжает работать)

На компьютере, с основного сервера ничего не меняя:

```bash
.venv/bin/python -m tools.deploy bundle --out ~/assistant-rehearsal
```

Папка содержит `code.tar.gz` (код из последнего коммита), `data.tar.gz` (вся `data/`: база, переписка, версии базы знаний),
`server.env` (настройки без путей и ключа Яндекса) и `SHA256SUMS`. В папке переписка клиентов и ключи: права 700, не
выкладывайте её в облака и почту, переписка должна оставаться в России. Выполните шаг 4 и проверьте шаг 5, но **в
`server.env` очистите `TELEGRAM_BOT_TOKEN`**: второй бот с тем же токеном мешает живому и забирает его сообщения.

## 3. Переезд

Сначала закоммитьте всё, потом:

```bash
deploy/mac-autostart.sh off
.venv/bin/python -m tools.deploy bundle --final --out ~/assistant-move
scp -r ~/assistant-move root@<сервер>:/root/
```

`--final` откажется работать, если бот ещё запущен или есть незакоммиченные правки.
**С этого момента бот на Mac не запускайте**: два бота с одним токеном конфликтуют.

## 4. На сервере

```bash
cd /root/assistant-move && sha256sum -c SHA256SUMS
mkdir -p /opt/assistant && tar xzf code.tar.gz -C /opt/assistant
install -m 600 server.env /opt/assistant/.env
cd /opt/assistant
nano .env                 # TELEGRAM_API_URL=https://tg.ваш-домен.ru
./setup restore /root/assistant-move/data.tar.gz --yes
./setup check
docker compose up -d --build --wait
```

## 5. Проверка

- `docker compose logs app | tail` — «Run polling», без Traceback и TelegramConflictError.
- С ноутбука: `ssh -L 8000:localhost:8000 root@<сервер>`, затем http://localhost:8000 — вход тем же логином и паролем.
- «Наблюдение»: те же чаты и сообщения, что были. Подключения: те же режимы.
- Написать боту с другого аккаунта и увидеть сообщение в админке.

## 6. Если не получилось

На сервере `docker compose down` (без `-v`), на Mac `deploy/mac-autostart.sh` — бот вернётся к прежним данным. Сообщения,
полученные на сервере, в базе Mac не появятся.

## 7. После переезда

- Копии: `./setup backup /root/backups/assistant-$(date +%F).tar.gz` раз в сутки по cron и забирать к себе (`scp`).
  Ежедневные копии внутри тома пропадут вместе с сервером. Хранить только в России.
- После проверки удалить `/root/assistant-move` и `~/assistant-move`, в них переписка и ключи.
- `GIGACHAT_VERIFY_SSL=false` переехал как есть: ключ GigaChat идёт без проверки сертификата. На сервере лучше добавить в образ
  корневой сертификат Минцифры и поставить `true`.
- Нерешённое для настоящего пилота: GigaChat физлица — только для некоммерческого использования; уведомление
  Роскомнадзора об обработке персональных данных; ключ Яндекса на сервер не переносится, но отозвать его всё равно нужно.
- MAX с московского сервера открывается напрямую, вебхук в адаптере ещё не сделан (см. CLAUDE.md, «Проверка MAX 30.10»).
