# Голосовые: GigaAM

## Что сделано

Голосовое клиента → локальная расшифровка → маскировка контактов → обычное ядро ответа → карточка менеджеру.
Содержательный ответ по расшифровке автоматически клиенту не отправляется, включая режим `auto`.
Менеджер проверяет названия, сроки и суммы, затем отправляет или редактирует черновик обычными кнопками.
Если ядро не может составить ответ, карточка содержит вопрос для менеджера.

| Канал и режим | Поведение |
|---|---|
| MAX, `draft` / `auto` | Менеджеру приходят исходное аудио, расшифровка и, когда возможен, черновик. Чат ставится на паузу |
| MAX, `observe` | Расшифрованный вопрос сохраняется в наблюдении, аудио пересылается менеджеру. Автоответа нет |
| MAX, голосовой ответ менеджера на карточку | Сначала клиенту доставляется исходное аудио, затем фоном извлекаются кандидаты. Расшифровка отдельно показывается менеджеру |
| Telegram Business, `draft` / `auto` | Голосовое клиента становится карточкой с расшифровкой и черновиком; голосовой ответ менеджера в чате клиента участвует в извлечении кандидатов |
| Telegram Business, `observe` | Голосовые обеих сторон проходят существующий журнал наблюдения и извлечение кандидатов |
| `off`, неутверждённое подключение, запрещённое наблюдение | Аудио не распознаётся |

Кандидаты проходят существующее ручное утверждение. Суммы из голоса не меняют прайс.
В Telegram голосовой ответ на карточку **в личном чате с ботом** пока не поддерживается:
менеджер отвечает голосом в исходном чате клиента. Текстовое редактирование карточки работает как раньше.

## Подключение

По умолчанию `SPEECH_ENABLED=false`. Рабочий `.env` и режимы подключений при разработке не менялись.
Основной бот и CI не требуют PyTorch: GigaAM запускается отдельным интерпретатором.

Локально на macOS, из корня проекта (для Linux — Docker-вариант ниже с CPU-библиотеками):

```sh
.venv/bin/python -m venv .venv/speech
uv pip install --python .venv/speech/bin/python -r requirements-speech.txt \
  --override requirements-speech-overrides.txt
```

Нужен `ffmpeg` в PATH процесса бота: на macOS — `brew install ffmpeg`, на Debian/Ubuntu —
`apt-get install ffmpeg`. `uv` используется и в основном проекте; если он установлен в `.venv`,
его путь — `.venv/bin/uv`. Override заменяет закреплённый GigaAM `onnx==1.19.*`, в котором аудит нашёл
известные уязвимости, на `1.22.0`. Наш worker использует PyTorch и не вызывает ONNX.
Это намеренное расхождение с метаданными upstream: `pip check` сообщит о несовпадении требования ONNX.
Сначала подготовить кэш весов под тем же пользователем, который запускает бота:

```sh
.venv/bin/python -m tools.prepare_speech
```

Только после успешной загрузки и проверки на контрольном аудио добавить в `.env`:

```dotenv
SPEECH_ENABLED=true
SPEECH_PYTHON=/абсолютный/путь/к/проекту/.venv/speech/bin/python
```

Веса берутся из официального [ai-sage/GigaAM-v3](https://huggingface.co/ai-sage/GigaAM-v3/tree/7655ad717f8122257385bb4b2f373db3697e8680).
Ревизия и SHA-256 трёх файлов закреплены в `app/speech_models.py`. Загрузчик сначала проверяет скачанный файл,
затем атомарно заменяет кэш. Повторная подготовка исправного кэша не обращается в сеть.
По умолчанию кэш лежит в `~/.cache/gigaam-hf/<ревизия>`; другой каталог задаётся через `SPEECH_MODEL_DIR`.
Во время распознавания загрузки нет: используются только проверенные локальные файлы.
Веса читаются с `weights_only=True`, удалённый `modeling_gigaam.py` не исполняется.

Нужен штатный перезапуск одного экземпляра бота. Не запускать второй `python -m app` рядом с рабочим.
Отключение: `SPEECH_ENABLED=false` и штатный перезапуск.

## Docker

Обычный образ остаётся без тяжёлых зависимостей. `Dockerfile.speech` расширяет его: отдельный Python,
CPU-сборка PyTorch, GigaAM и ffmpeg. Веса живут в отдельном томе `speech-model`, записи — во временном `/tmp`.
Корневая файловая система остаётся только для чтения, процесс работает от пользователя 10001.
Для Linux torchaudio также устанавливается из CPU-индекса; setuptools из этого индекса обновляется
до исправленной версии 84.1.0. Одного CPU-варианта PyTorch недостаточно: torchaudio из PyPI требует CUDA.

```sh
docker compose build app
docker compose -f docker-compose.yml -f docker-compose.speech.yml build app
docker compose -f docker-compose.yml -f docker-compose.speech.yml run --rm --no-deps app \
  python -m tools.prepare_speech
docker compose -f docker-compose.yml -f docker-compose.speech.yml up -d --wait
```

Последняя команда включает голосовые в контейнерном экземпляре: override устанавливает `SPEECH_ENABLED=true`.
Перед ней проверить запись вручную. Не поднимать этот экземпляр одновременно с рабочим ботом на Mac.
Для проверки без Telegram/MAX нужен отдельный `.env` без их токенов, `LLM_PROVIDER=mock`, отдельное имя Compose-проекта
и свободный порт. `ASSISTANT_ENV_FILE` выбирает файл окружения, `ASSISTANT_PORT` — порт.

Том модели не содержит переписку и не включается в бэкап бизнес-данных: его можно повторно скачать.
Откат к обычному образу: пересоздать `app` по одному `docker-compose.yml`; в рабочем `.env` при этом
должно быть `SPEECH_ENABLED=false` или не быть этого флага. `down -v` удалит тома, для отключения он не нужен.
Текущий `deploy/release.sh` использует обычный Compose и не выкладывает speech-образ: автоматизацию выпуска
этого варианта нужно подключать отдельно, после проверки на целевом сервере.

## Ограничения и данные

- Одна запись: до 2 минут и 20 МБ. Длительность проверяется по декодированному звуку, не только по метаданным.
- Распознавание на CPU, модель `v3_e2e_rnnt`; один дочерний процесс за раз, не более четырёх запросов внутри распознавателя.
- Таймаут распознавания вместе с ожиданием — 180 секунд; загрузки аудио MAX — 30 секунд; декодирования — 30 секунд.
- Записи разбиваются на фрагменты по 20 секунд. На границе слова могут распознаваться хуже;
  названия ТЦ, числа, шум и быстрая речь требуют отдельного замера.
- Модель загружается в память заново на каждую запись. Задержка и расход памяти на целевом сервере ещё не измерены.
- MAX обрабатывает голосовые отдельно от текстов других клиентов, до четырёх операций одновременно.
  Последующие сообщения того же чата ждут голосовое. Событие остаётся в SQLite до завершения;
  отмена обработки возвращает его для повтора после запуска.
- Временные оригинал, WAV и фрагмент удаляются после успеха, ошибки и отмены. При таймауте останавливается группа
  дочерних процессов, включая ffmpeg. Аварийное выключение всей ОС не даёт гарантии удаления временного каталога.
- Оригинал остаётся в самом мессенджере и в пересланном менеджеру сообщении. Это не архив аудио на сервере бота.
- Телефоны, почта и другие шаблоны существующего `mask_pd` скрываются **до** передачи текста ядру.
  Это не полная анонимизация: номер, произнесённый нестандартно и распознанный словами, может не совпасть с шаблоном.
- Аудио не отправляется в облако распознавания. Маскированный текст может поступать в настроенный GigaChat
  для черновика или извлечения кандидатов, как обычная переписка.
- Внешние аудиоссылки MAX разрешены только по HTTPS на публичные IP, без редиректов и без передачи токена бота.
  Соединение закрепляется за проверенным IP; проверка сертификата и SNI сохраняются.
- Если распознавание не удалось, используется прежняя передача медиа менеджеру. В `auto` возможна
  прежняя служебная фраза ожидания; ответа на содержание записи нет.

## Проверка команды: 30 записей

Записать десять обычных вопросов, десять с шумом и десять с быстрой речью, паузами и исправлениями.
Включить «ВЕЕР», «ДЕПО», суммы словами, срок размещения, торг и вопросы, которые надо передавать менеджеру.
Эталоны расшифровать вручную до просмотра результата модели. Не использовать реальные контакты клиентов.
Записи и CSV хранить вне репозитория.

Пример `manifest.csv` рядом с папкой записей:

```csv
audio,reference
audio/01.ogg,Сколько стоит экран в атриуме ВЕЕР Молл на месяц
audio/02.ogg,Можно за двадцать тысяч на две недели
```

Запуск из корня проекта:

```sh
.venv/bin/python -m eval.speech_eval /путь/manifest.csv \
  --python "$PWD/.venv/speech/bin/python" --output /путь/voice-results.csv
```

Скрипт считает WER: сумму замен, пропусков и вставок, делённую на число эталонных слов.
Регистр, пунктуация и `ё/е` не учитываются; числа словами и цифрами автоматически не уравниваются.
Также сравнивает решение ядра по эталонному тексту и по распознанному. Используется рабочая черновая KB
`data/kb`, модель ответа — **MockProvider**, без сети и расходов на GigaChat. Это диагностическая метрика
правил маршрутизации, а не измерение качества ответов настоящего GigaChat. Фиксируйте версию KB вместе с результатом.
CSV результата содержит имя файла, число слов, ошибки, совпадение решения и тип ошибки; тексты туда не записываются.

Автоматические проверки:

```sh
.venv/bin/python -m pytest -q tests/test_speech.py tests/test_speech_models.py tests/test_voice.py
make check
```

Проверяются ручная отправка в `auto`, оба канала, обучение из ответа менеджера, отзыв наблюдения,
выключенный канал, маскировка, размер, таймаут с очисткой, разбиение длинного аудио,
очередь MAX и сохранение незавершённого события. При установленном ffmpeg отдельно проверяется
реальное декодирование записи длиннее лимита; без него этот тест пропускается.

## Результат на 07.11.2026

`make check`: 1196 тестов, покрытие 86%; отдельный набор голосовых и загрузчика — 31 тест.
`make security` прошёл, отдельная проверка Dockerfile.speech через Semgrep — без находок.
После замены ONNX аудит окружения распознавания не нашёл известных уязвимостей среди проверенных пакетов;
GigaAM 0.2.0 из Git пропущен аудитом, поскольку эта версия не представлена в PyPI.

Первый CDN GigaAM возвращал `CERTIFICATE_VERIFY_FAILED: certificate has expired`.
Перешли на официальную копию Hugging Face, закрепили ревизию и SHA-256. Проверку TLS не отключали.
Реальный запуск также обнаружил изменение API библиотеки: `transcribe()` возвращает объект
`TranscriptionResult`, поэтому worker теперь берёт его поле `.text`.

Локальная проверка на Apple Silicon, CPU, два потока, с загрузкой модели на каждую запись:

| Запись | Время обработки |
|---|---:|
| Открытый речевой пример, 11,29 секунды | 3,87 с |
| Синтетический вопрос о размещении экрана и длительности ролика | 2,28 с |
| Быстрая синтетическая речь с исправлением ТЦ и срока | 2,27 с |
| Та же открытая запись, повторённая до 33,87 секунды, несколько фрагментов | 3,39 с |

Пиковая память дочернего процесса на коротких записях — около 1,47 ГиБ.
Docker проверен в Colima на Linux ARM64, 2 CPU и 3 ГиБ памяти виртуальной машины:
три короткие записи распознаны за 5,75–8,13 с при `--network none`, `--read-only` и UID 10001.
Временных файлов после распознавания нет. Отдельный Compose-проект без токенов Telegram/MAX прошёл
запуск и пересоздание: `/health` вернул `{"ok": true}`, модель сохранилась в своём томе,
распознавание из пересозданного контейнера прошло. Чистая подготовка тома проверена копированием
проверенного кэша и повторной сверкой SHA-256; загрузчик отдельно скачал конфигурацию и токенизатор по HTTPS.
Повторно скачивать 428 МБ весов для Docker-проверки не потребовалось.

Аудит Python-зависимостей speech-окружения готового образа после исправлений — без известных уязвимостей.
Для проверки CPU-пакетов использованы базовые версии без суффикса `+cpu`; GigaAM из Git не входит
в проверку PyPI. `eval.ci_gate` — не хуже эталона. x86-сервер и живые каналы этим прогоном не проверялись.

Это проверка работоспособности, не статистический замер качества. В одном синтетическом примере
«ВЕЕР» распознан как «Вейер», что подтверждает необходимость ручной проверки названий.
Набора из 30 человеческих записей команды ещё нет; WER на реальных клиентских голосовых не измерен.

Открытая запись взята из [примера GigaAM в sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx/blob/master/scripts/nemo/GigaAM/run-rnnt-v2.sh),
с указанного там зеркала аудио. Синтетические записи сделаны локальным голосом Milena macOS.
Клиентские записи не использовались. В рабочем боте функция не включена.

Исходный код и установка модели: [salute-developers/GigaAM](https://github.com/salute-developers/GigaAM).
Версия библиотеки закреплена коммитом в `requirements-speech.txt`; отдельного lock-файла транзитивных зависимостей пока нет.
