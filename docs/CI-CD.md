Сделано 07.11.2026 по замечанию руководителя на первой встрече. Голосовые (второе замечание) делает Codex —
`docs/VOICE.md`.

## CI: проверки на каждый push

`.github/workflows/ci.yml` — на каждый push в `main`, на pull request и вручную. Модель — заглушка, Telegram и MAX
не подключаются, ключей нет: сеть нужна только для зависимостей и базы уязвимостей. Три задачи идут параллельно:

| Задача | Что проверяет |
|---|---|
| Линтер, тесты, экзамены (Python 3.11 и 3.13) | `make check` — Ruff и все автотесты с покрытием; `python -m eval.ci_gate` — все `eval/questions*.csv` на заглушке и экзамен обучения без сети не хуже эталона `eval/ci_baseline.json` |
| Безопасность | `make audit` (pip-audit по lock-файлу), gitleaks по всей истории git (бинарник проверяется по контрольной сумме), Bandit |
| Сборка и запуск в Docker | `deploy/container/smoke.sh`: чистая установка, `/health`, пересоздание контейнера, бэкап, восстановление SQLite и файлов |

Эталон экзаменов. Заглушка отвечает первым найденным фрагментом, поэтому её цифры ниже GigaChat, — эталон ловит
не качество модели, а поломку: правка поиска, стоп-тем, проверок или базы, после которой в каком-то наборе стало больше
опасных ответов или меньше верных решений. Стало лучше — обновить эталон отдельной правкой и написать почему.
`ci_gate` берёт базу без папки `data/kb/notes/Из переписки/`: факты из настоящей переписки в git не уходят,
и локальный итог должен совпадать с CI.

```bash
.venv/bin/python -m eval.ci_gate            # как в CI
.venv/bin/python -m eval.ci_gate --update   # записать новый эталон
```

Проверено 07.11 без GitHub: дерево файлов, которое попадёт в коммит (без `.env`, баз и игнорируемого), в чистых
контейнерах `python:3.11-slim` и `python:3.13-slim` с `TZ=UTC` — 1163 теста прошли, 2 пропущены (им нужны локальные
прогоны симуляции, их нет в git), эталон экзаменов совпал; pip-audit — уязвимостей нет; Bandit — без находок; gitleaks
по истории и по дереву — утечек нет; Docker smoke — `SMOKE OK`. На самом GitHub workflow заработает после push.

## CD: выкладка на сервер

Сервер ещё не куплен, поэтому выкладка подготовлена и проверена на учебном «сервере» (Colima), но не включена.

- `deploy/release.sh <тег>` — на сервере, в git-клоне проекта: бэкап данных (`./setup backup`, бот стоит секунды) →
  новая версия (`git checkout`, `docker compose build`, `up --wait`) → `/health` изнутри контейнера. Не поднялась —
  прошлый образ (`ai-sales-assistant:previous`), прошлый код и данные из бэкапа. Журнал — `../backups/releases.log`.
  Коды выхода: 0 — новая версия работает; 1 — откатились, прошлая работает; 2 — не поднялась и прошлая, нужен человек.
- `.github/workflows/deploy.yml` — по тегу `v*` или вручную: те же проверки CI, затем SSH на сервер и `release.sh`.
  Пока нет переменной `DEPLOY_HOST`, шаг выкладки пропускается.

Проверено 07.11 в Colima (профиль `ai-sales-test`, отдельный Compose-проект): версия A → выкладка B — `exit 0`, данные
на месте; выкладка C, которая при старте портит данные и падает, — `exit 1`, работает B, данные из бэкапа, `/health` 200.

### Включить, когда будет сервер

1. На сервере: пользователь `deploy` в группе `docker`, Docker Engine и Compose 2.30+.
2. Клон проекта по deploy-ключу только для чтения (GitHub → Settings → Deploy keys), в папке — `.env` с ключами
   (`./setup` или перенос по `docs/ПЕРЕНОС.md`), первый запуск `docker compose up -d --build --wait`.
3. Отдельная пара SSH-ключей для GitHub → сервер: публичный — в `~deploy/.ssh/authorized_keys`, приватный — в секрет
   репозитория `DEPLOY_SSH_KEY`; вывод `ssh-keyscan <адрес>` — в секрет `DEPLOY_KNOWN_HOSTS`.
4. Переменные репозитория: `DEPLOY_HOST`, `DEPLOY_USER` (`deploy`), `DEPLOY_DIR` (папка клона).
5. Окружение `production` (Settings → Environments) с обязательным подтверждением — выкладка ждёт кнопку человека.

Выпуск версии: `git tag v2026.11.20 && git push origin v2026.11.20`. Вернуть прошлую руками на сервере:
`./deploy/release.sh <прошлый тег>`.

Что уходит на GitHub: только код. Данные клиентов, `.env` и ключи модели остаются на сервере в РФ; на GitHub — SSH-ключ
пользователя `deploy`. Экзамены на настоящем GigaChat в CI не гоняем: ключ не должен уходить на GitHub, а модель
принимает один запрос за раз. Их место — ночной запуск на сервере по расписанию (следующий шаг).

Бэкапы перед выкладкой не удаляются сами: раз в месяц проверить место на диске.
