# Сравнение BM25, GigaChat embeddings и RRF

Стенд `eval/retrieval_eval.py` отделён от отвечающего бота. Он не меняет `app/core/knowledge.py`,
промпт или активную базу. Не вызывает чат-модель. Работает с теми же разделами KB и строками
прайса, но измеряет поиск источников, а не корректность готового ответа.

## Что сравнивается

- **BM25:** штатный `KnowledgeBase.search` с нормализацией запроса.
- **Embeddings:** косинусная близость нормированных векторов GigaChat.
- **RRF:** сумма `1 / (60 + rank)` двух выдач, по умолчанию глубина каждой 60.

Фильтры названной площадки и цен для арендаторов одинаковы для всех методов. В отличие от
полного `KnowledgeBase.retrieve` стенд не строит каталог и не подбирает товары по бюджету.
Это сравнение ранжирования, а не трёх полных вариантов ассистента.

У вопросов с `dialog` запрос содержит три предыдущие реплики клиента из того же сценария.
Ответы, `must_contain` и эталонные документы в запрос не добавляются. Все строки `questions*.csv`
получают выдачу, но Recall/MRR считаются только для вопросов с положительной проверенной разметкой.
Отказы, приветствия и неразмеченные вопросы не засчитываются как ошибки поиска.

## Источники и разметка

В исходном наборе из 47 связей метка `team-review` обозначает предварительную сверку по источникам с помощью ИИ-ассистента. Отдельная ручная приёмка участником этой меткой не подтверждается.

```bash
.venv/bin/python -m eval.retrieval_eval --prepare
```

В `eval/retrieval_results/` появятся:

- `corpus.csv`: ID, исходный ID фрагмента, тип, заголовок и полный текст.
- `queries.csv`: исходная формулировка, запрос с историей, набор и номер строки.
- `qrels_draft.csv`: предложения пар вопрос–источник для проверки. `relevance` и `reviewer` пустые.

ID документа зависит от типа и полного текста, а не от порядкового номера в файле. ID вопроса
фиксирует набор, строку и контекст. Если вопрос, история или документ изменились, старая разметка
не принимается молча. Хеш полного корпуса и разметки сохраняется в отчёте. Изменение KB во время
её загрузки прерывает запуск, чтобы не смешивать версии.

Существующее `must_contain` проверяет слова в готовом ответе, но **не размечает источники**.
Совпавшая сумма может относиться к другой площадке. Поэтому автоматические предложения остаются
черновиком и не входят в метрики до заполнения полей:

```csv
query_id,document_id,relevance,reviewer,note
q-<ID из queries.csv>,d-<ID из corpus.csv>,1,manager,проверены услуга и условия
```

Шкала: 0 — не подходит, 1 — релевантен, 2 — полностью покрывает вопрос. Метрики сейчас бинарные:
1 и 2 считаются положительными. Несколько обязательных источников размечаются отдельными строками.
Пустые reviewer/relevance игнорируются. Противоречащие оценки одной пары блокируют запуск.

Для цены разметка должна указывать соответствующую строку прайса с правильной площадкой,
единицей и типом клиента. Для содержательных правил — соответствующие разделы заметок.

В `eval/retrieval_qrels.csv` есть начальная разметка **40 вопросов / 47 связей** из всех шести
наборов, выполненная разработчик 2 по текстам источников (`reviewer=team-review`). Она ещё не
проверена менеджером, не исчерпывает все релевантные документы и смещена к понятным ценовым
вопросам. Её результат подходит для первого технического прогона, не для заявления качества
на всех 480 вопросах. Для исследовательского вывода расширьте и независимо проверьте разметку,
включая сложные сообщения. Переформулировки одного вопроса не считайте независимыми диалогами.

## Запуск

Только BM25, без сети:

```bash
.venv/bin/python -m eval.retrieval_eval --methods bm25
```

Все три метода, с разрешением запросов к embedding API:

```bash
.venv/bin/python -m eval.retrieval_eval --allow-api --embedding-model Embeddings-2
```

Повтор по готовому кешу, без сетевых запросов:

```bash
.venv/bin/python -m eval.retrieval_eval
```

Отдельные наборы можно передать через `--questions eval/questions.csv eval/questions_live.csv`.
Но qrels должны содержать только эти вопросы: чужие или устаревшие ID блокируют запуск.
Для отдельного эксперимента используйте собственные `--qrels`, `--out` и `--cache`.

Настройки ключа, scope, TLS и адреса берутся через `Settings.load` из окружения/`.env`.
Новых секретов в скрипте нет. По умолчанию используется Embeddings-2. Для EmbeddingsGigaR
задайте инструкцию только для запросов:

```bash
.venv/bin/python -m eval.retrieval_eval --allow-api --embedding-model EmbeddingsGigaR \
  --query-instruction $'Дан вопрос, необходимо найти абзац текста с ответом\nвопрос: '
```

Кеш SQLite хранит нормированные векторы по хешу текста, модели, API-адреса и инструкции.
Размерности проверяются. Пакеты последовательные (по 10 строк), кеш сохраняется после каждого,
повторный процесс с тем же кешем блокируется. Сеть включается только флагом `--allow-api`.
Эмбеддинги оплачиваются отдельно от чат-модели.

## Метрики и выходные файлы

| Метрика | Определение |
|---|---|
| Recall@k | Число размеченных релевантных источников в top-k / все размеченные релевантные источники вопроса |
| Hit@k | 1, если в top-k есть хотя бы один релевантный источник, иначе 0 |
| MRR | Среднее `1 / rank` первого релевантного источника по полной выдаче метода |
| MRR@k | Та же величина, но источник вне top-k даёт 0 |

Средние макро: каждый размеченный вопрос имеет одинаковый вес. У RRF полная выдача ограничена
объединением двух списков глубины `--depth`; это ограничение видно в report.json. Сравнивайте
также одинаковый MRR@k, а не только MRR по спискам разной длины.

`metrics.csv` содержит по одной строке на вопрос и метод; `rankings.json` — полные выдачи и
размеченные положительные ID; `report.json` — агрегаты по наборам и в целом, хеши, параметры,
число API-запросов и фактические токены из ответов провайдера. Корпус и запросы сохраняются рядом.

`retrieval_ms` измеряет локальное ранжирование, **не сетевую задержку получения вектора запроса**.
`embedding_prepare_ms` показывает общее время получения/загрузки векторов. Эти числа нельзя
выдавать за сквозную задержку готового бота. Сетевой p95 нужно измерять отдельным опытом.

## Проверенный результат 21.10.2026

На начальной разметке 40/480, k=8: BM25 Recall@8 = 0,8875, MRR ≈ 0,654, Hit@8 = 0,95.
Это неполная разметка, не независимая проверка менеджера.

Живые запросы к `Embeddings-2`, `Embeddings` и `EmbeddingsGigaR` вернули **HTTP 402**.
Доступной квоты на embedding API у использованного ключа не оказалось. Реальные результаты
эмбеддингов и RRF поэтому не получены. Скрипт поддерживает их, но отчёт BM25 ими не подменялся.
После подключения квоты команда `--allow-api` продолжит эксперимент, кеш не требует изменения ядра.

Набор тестов проверяет формулы Recall/Hit/MRR, RRF, контекст без утечки эталона, ID документов,
одинаковые фильтры, разбор индексов GigaChat, кеш и полный offline-прогон трёх методов на
синтетических векторах. Синтетический тест не является результатом сравнения моделей.

Первичные источники: [GigaChat embeddings](https://developers.sber.ru/docs/ru/gigachat/guides/embeddings),
[RRF, Cormack et al.](https://plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf),
[BEIR](https://arxiv.org/abs/2104.08663).
